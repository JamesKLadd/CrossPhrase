This is an Expo/React Native mobile application. Prioritize mobile-first patterns, performance, and cross-platform compatibility.

## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.

## Commands

Use `bunx` instead of `npx` if the project uses bun (`bun.lock` present).

```bash
npx expo install <package>  # ALWAYS use instead of npm/yarn/pnpm/bun add — resolves SDK-compatible versions
npx expo start              # start the dev server
npx expo lint               # lint
npx tsc --noEmit            # typecheck
npx expo-doctor             # diagnose dependency and config issues
npx expo install --fix      # fix incompatible package versions
```

Run lint and typecheck before declaring any task done.

## Navigation & Routing

- Use **Expo Router** for all navigation. Routes live in `src/app/` — every file there is a screen, `_layout.tsx` files define navigators. Keep non-route code (components, hooks, utils) outside `src/app/`.
- Import `Link`, `router`, and `useLocalSearchParams` from `expo-router`.
- Docs: https://docs.expo.dev/router/introduction.md

## Building with EAS

Use EAS to build, sign, and submit the app in the cloud (`eas build`, `eas submit`) and to ship over-the-air updates (`eas update`) — no local Xcode or Android Studio required. Run EAS CLI as `bunx eas-cli <command>` in Bun projects, or `npx eas-cli@latest <command>` otherwise; substitute that for bare `eas` in docs examples.
Docs: https://docs.expo.dev/eas/index.md

## Rules

- If `ios/` and `android/` directories do not exist, they are generated (Continuous Native Generation). Never create or edit them by hand — configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, the app needs a development build: `npx expo run:ios|android` locally, or `eas build --profile development`.
- Prefer recommended Expo modules over third-party libraries, and check your available skills before adding dependencies. Docs: https://docs.expo.dev/versions/latest/index.md

## CrossPhrase project notes

- Design and phase plan: `docs/DESIGN.md`. Setup and commands: `README.md`.
- Keep `src/core/` free of React and Expo imports. It is the game's rules and
  must stay unit-testable (and reusable server-side for leaderboard checks).
- Game state changes only go through `gameReducer` in `src/core/game.ts`.
- `src/data/words.json` and `supabase/functions/_shared/dictionary.json` are
  generated by `scripts/build_words.py`, and `src/data/grammar.json` by
  `scripts/build-grammar.mjs` (`npm run build:words` runs both). Edit
  `scripts/words/*.txt` instead.
- `supabase/functions/` is Deno code and is excluded from the app's tsconfig.
  Keep request logic in `judge/judge.ts` (dependency-injected and tested in
  `judge_test.ts`); `index.ts` only wires Supabase and Anthropic in.
- Database changes go in a new file in `supabase/migrations/`, with tests in
  `supabase/tests/database.test.mjs`. Never edit a migration that has shipped.
- The judge prompt every judge uses is `supabase/functions/_shared/judgePrompt.ts`;
  changing it means bumping `PROMPT_VERSION`.
- Judges: the PC judge (`pc-judge/`, Node via tsx, reuses `judge/judge.ts`), the
  built-in judge (`src/core/localJudge.ts` + `tinyJudge.ts`, model in
  `src/data/judgeModel.json`, retrained by `npm run train:judge`), and the
  optional Claude judge (Supabase). Never commit test labels or verdicts in
  `training/`; it holds the developer's real data.
- Levels 1-10 are the scripted tutorial in `src/data/tutorial.ts`; tests check
  the bot can clear each one with its deck. Levels 11+ are in
  `src/data/levels.generated.json`, written by `npm run generate:levels`
  (`src/core/levelGen.ts` + the bot in `levelBot.ts`). Never hand-edit that
  file. The bot plays only lines `isGrammatical` (`src/core/grammar.ts`)
  accepts, so every level has a real-English answer; keep it that way, and
  keep the built-in judge passing every grammatical line. Never change how an
  existing board deals (`drawTile` in `src/core/game.ts`): a new dealing rule
  gets a new `draw` version, since old runs must replay identically. Each
  generated board's proof (the bot's moves, `src/core/proof.ts`) is in
  `src/data/proofs.generated.json`, written by the generators and replayed
  by `solvable.test.ts`; never import it into the app or the server bundle. Changing word lists, the built-in judge model, `LEVEL_BANDS` or other
  knobs in `src/core/config.ts` changes what the generator makes, so only
  regenerate deliberately (it reshuffles levels players have already seen).
- Every game records a run log (`src/core/run.ts`); `replayRun` rebuilds a
  game from it. The daily puzzle resumes this way, and the leaderboard server
  (`src/server/scores.ts`, bundled into `supabase/functions/_shared/scores.bundle.js`
  by `npm run bundle:server`) scores runs only by replaying and re-judging
  them with the built-in judge. After changing `src/core`, word lists, the
  judge model, levels or dailies, run `npm run bundle:server`; a Jest test
  fails while the bundle is stale. Daily puzzles live in
  `src/data/dailies.generated.json` (`npm run generate:dailies -- --from <day>`,
  which keeps earlier days); never hand-edit them, never change a day that has
  been played, and keep the daily judged by the built-in judge.
- Player progress lives in `src/progress/` and settings in `src/settings/`
  (device storage); the developer tools behind the PIN are `src/app/dev/`.
- `assets/sounds/*.wav` are generated by `npm run make:sounds`
  (`scripts/make-sounds.mjs`); edit the script, not the files. Play sounds and
  haptics only through `src/ui/feedback.ts`, which respects the settings.
- Animations must respect reduced motion (`useReduceMotion()` from
  `src/settings`): skip or shorten them when it's on. Verdict colours come from
  `useTierColors()` and always go with a `TIER_ICON`, never colour alone.
- New native libraries must be in Expo Go's bundle
  (`node_modules/expo/bundledNativeModules.json`) and installed with
  `npx expo install`, since the developer tests in the App Store's Expo Go.
  Anything new must also work on the web: the game ships as a website
  (`npm run build:web`, published to GitHub Pages by
  `.github/workflows/website.yml`), so guard native-only APIs with
  `Platform.OS` and check `npm run build:web` still succeeds.
- The economy (hearts, feathers, boosters) is pure logic in
  `src/core/economy.ts`; the wallet store is `src/economy/`. Boosters are
  reducer actions and run actions, and `parseRun` refuses them so boosted
  runs never reach leaderboards. Hearts and boosters only apply from
  `ECONOMY_FROM_LEVEL`; the daily and zen never use them.
- Remote config (`src/remote/`, the `remote_config` table) feeds
  `parseEconomy` and `parseTuning`; both must ignore anything malformed and
  fall back to defaults. Level tuning (`src/core/tuning.ts`) is applied by
  both the app and the leaderboard server; never tune the tutorial or the
  daily puzzles.
- Accounts: `src/account/` (client, cloud-save merge and sync), the `account`
  function, and `supabase/functions/_shared/accountRules.ts` (username and
  password rules, imported by both the app and the function). Account users
  are Supabase Auth users with a made-up `<username>@players.crossphrase.invalid`
  email that's set already confirmed, so no mail is ever sent. Cloud-save
  merges must never lose progress (`mergeSaves`): keep anything new in a save
  mergeable the same way, and keep feathers in the wallet ledger, never as a
  plain balance. Leaderboard names come from `accounts.username`.
- Admin: the `admins` table (by user id, seeded with James's and Kimberly's (kimberlymladd) accounts, each in a migration) and
  `is_admin()`. Every admin RPC (`admin_*` in the admin migration) calls
  `require_admin()` itself; the app's `admin` flag and `DevGate` only decide
  what's shown, so never rely on them for security. Admin screens live in
  `src/app/dev/`, their API in `src/admin/`. Training labels go to the
  `labels` table through `submit_label` (`src/labels/`); players' wait for
  review, the admin's are approved at once; `npm run pull:labels` brings the
  approved ones to `training/labels.jsonl`.
- Play stats go through `track()` in `src/analytics/` (queued, batched,
  switchable in Settings). Never put anything a player typed in an event
  except the feedback they choose to send, and no names.
- Before declaring work done: `npm test`, `npm run typecheck`, `npm run lint`,
  plus `npm run test:pc-judge` when touching `pc-judge/`, and `npm run test:db` /
  `npm run test:functions` when touching `supabase/`.
